# Upgrading Notion Automator

> **Draft.** The version-specific section lists changes that are already made on the development branch and not yet released.

## Every upgrade

1. **Stop the daemon.** Linux service: `sudo systemctl stop notion-daemon`. Windows service: stop "Notion Automator" in `services.msc`. Wait for it to stop before touching any file: two copies running at once will both write to Notion.
2. **Back up your local files.** Copy `config.toml`, `config_secrets.toml`, `config_hub_state.toml` and, once it exists, `config_automations.toml` somewhere safe. None of them is in the repository, so an update will not replace them, but a backup costs nothing.
3. **Get the new version.** `git pull` in the project folder, then `pip install -r requirements.txt` inside your virtual environment (the Notion client package is pinned there and the daemon refuses to start on an older one).
4. **Read the changes.** Check the release notes and the version-specific section below for anything you must change by hand.
5. **Make the changes.** Compare your `config.toml` with [`config_example.toml` (project folder)](../config_example.toml): new options appear there first, commented out, with an explanation.
6. **Start the daemon and read the log.** The first lines show the version, where the token was read from and whether the Configuration Hub is on. Fix anything the log reports before you rely on it.

## Next release (changes on the development branch)

- **The token file is renamed.** `secrets.toml` is now `config_secrets.toml`, so it sorts next to `config.toml`. Rename your file, and copy [`config_secrets_example.toml` (project folder)](../config_secrets_example.toml) if you need the template. On Windows, run the `icacls` line from `install-service.ps1` again for the new name, because the access rights belong to the old file name. If you forget, the daemon stops with "No Notion token" and tells you the file was renamed.
- **The Configuration Hub is optional.** Without `config_hub_data_source_id` in `config.toml` the daemon runs without it. See "Setting up the Configuration Hub" in the README.
- **Switching a row off now takes effect without a restart.** Setting a config row's Status to anything other than Active stops that row's automations on the next poll. Removing a recurring-tasks block from an Active row stops it too.
- **What to automate moves out of `config.toml`.** The `[[databases]]` and `[recurring_tasks]` tables and `non_completion_statuses` are no longer read. If `config.toml` still has them, the daemon stops at startup and prints the converted text. Paste that text into a config row's code block (Hub), or save it as `config_automations.toml` next to `config.toml` (no Hub), then delete the old entries from `config.toml`. Each `[[databases]]` becomes a `[[property_automations]]` block: `id` becomes `data_source_id` (use the data source ID; a database ID is accepted with a warning), `closed_date = true` becomes `closed_date_property = "Closed Date"`, `reopen_count = true` becomes `reopen_count_property = "Reopen Count"`, `first_value_fields` and `update_count_fields` become `first_value_properties` and `update_count_properties`. The `[recurring_tasks]` table becomes a `[[recurring_tasks]]` block (double brackets; the single-bracket form is an Error, and one row may hold several blocks, one per pair): `definitions_db_id` and `tasks_db_id` become `definitions_data_source_id` and `tasks_data_source_id`, and the `enabled` key is gone: comment the block out to switch it off. A data source is in one block only, as a definitions or a tasks data source, never both.
- **Recurring task copy settings are renamed.** `inherited_properties` is now `inherit_include_properties` (a list, or the string `"all"`), with the new `inherit_exclude_properties` and `inherit_icon`. A row that still has the old key shows an unknown-key Warning and copies nothing until you rename it.
- **There is one config data source and no kill switch.** Remove `status_data_source_id` from `config.toml` (the daemon warns while it is there), and pause the Automator by setting its config row's Status to anything but Active.
- **The bot keeps a copy of the applied config.** `config_automations.toml` is written after each apply that had no Errors, and restores the config row if it is deleted. Back it up with the other local files; it is gitignored. A file with that name that you wrote yourself is never overwritten: rename it first.
- **A deleted config row is recreated** (at most `hub_max_recreations` times in a row, default 2). See the README, "If the config row is deleted".
